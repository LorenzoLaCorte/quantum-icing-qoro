# Quantum Icing: the network23 website

A static site that replays how QOBLIB `network23` went from 657,121 (our network24 hand-in) to the checked
**632,319**, 4.10% below the best known value. There is no build step. Three.js and GSAP are vendored in `vendor/`.

## Preview locally

```bash
python3 -m http.server 8000 --directory website
# open http://localhost:8000
```

Opening `index.html` straight from disk does not work, because the page fetches `data/network23_story.json`.

## Deploy on Render

- **Blueprint:** push the repo, then in Render choose *New → Blueprint* and pick this repository. `render.yaml` at the
  repo root defines a static site that publishes `website/`.
- **By hand:** *New → Static Site*, connect the repo, leave the build command empty (or `echo ok`), and set the publish
  directory to `website`.

## Where the data comes from

`data/network23_story.json` is generated by `tools/build_story.py` from the checked solution files:

```bash
.venv/bin/python website/tools/build_story.py /tmp/replay   # about 6 minutes, 2 LP workers
```

The script rebuilds every act from real files and a real replay:

1. the `network24` hand-in (657,121);
2. node 24 deleted and its links spliced, as in the hybrid chain (642,084);
3. the two 2-exchanges that lead to the `network23` hand-in (639,739);
4. a replay of `network_design/quantum_congestion.py` with the `walk23` settings (seed 73, 52 rounds). It logs each
   round's pool, oracle marking, measured shots, LP scores and the move taken, and it asserts that it reaches the
   checked `deliverables/network_quantum/network23.sol` (632,319).

Link loads come from a two-stage routing LP: minimum congestion first, then the least total flow at that congestion.
About half of the 46 links carry the maximum load, which is typical of a min-max routing, so the colour scale is
relative to the busiest link and gold marks the saturated links.
